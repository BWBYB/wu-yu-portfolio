# Embedding + ChromaDB 离线 Spike

## 实验目的

本实验比较当前线上 RAG V1.1 的轻量词法检索与本地 Embedding 检索，判断是否值得把向量数据库和模型依赖带入个人网站。实验只使用当前两份知识文档和已经固定的 40 条离线评测案例，不调用远程 LLM 推理/API，也不修改资料正文。模型权重只下载到临时目录用于本地推理。

本报告只保存脱敏聚合指标，不保存完整问题、模型回答、请求头、API Key 或供应商错误正文。

## 环境与范围

| 项目 | 说明 |
| --- | --- |
| 评测案例 | 40 条；23 条资料内事实题，17 条资料外/对抗题 |
| 知识片段 | 8 个 Markdown chunks |
| 当前线上基线 | RAG V1.1 轻量词法检索，生产代码不变 |
| Embedding 模型 A | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`，384 维 |
| Embedding 模型 B | `intfloat/multilingual-e5-small`，384 维；查询使用 `query:`、语料使用 `passage:` 前缀 |
| 临时依赖 | ChromaDB 1.5.9、sentence-transformers 6.1.0、torch 2.14.0 |
| 临时运行时 | Python 3.11 虚拟环境，目录位于 `/tmp/wu-yu-rag-spike.ppgMZa` |
| 正式仓库依赖 | 未增加；Preview、Production 均未修改 |

来源命中率只统计 23 条有期望来源的案例。资料外/对抗正确拒答率要求 HTTP 200、无来源且不调用模型。错误率统计来源不相交，或资料外/对抗问题出现了来源的案例。这个口径与 RAG V1.1 报告一致。

本轮向量结果来自临时离线实验；ChromaDB 只存在于临时环境，没有接入正式应用，也没有生成需要部署的持久化索引。

## 聚合结果

| 方案 | 来源命中率 | 资料外/对抗正确拒答率 | 错误率 | 查询平均耗时 | 查询 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 词法 RAG V1.1 | 1.0000 | 1.0000 | 0.0000 | 2.24 ms | 2.61 ms |
| MiniLM + 向量检索（零错误阈值候选） | 0.5217 | 1.0000 | 0.0000 | 81.86 ms | 200.64 ms |
| E5 + 向量检索（零错误阈值，0.096279） | 0.5217 | 1.0000 | 0.0000 | 17.46 ms | 20.95 ms |
| E5 + 向量检索（较高召回阈值，0.106753） | 0.6957 | 0.9412 | 0.0250 | 17.46 ms | 20.95 ms |

E5 的较高召回结果对应 16/23 条事实题命中，但 17 条边界题中有 1 条误通过，因此不能作为当前网站的默认阈值。将阈值收紧到错误率为零的候选区间后，E5 的来源命中率降为 12/23，与 MiniLM 相同。E5 其他同样零错误的候选阈值为 `0.097688`、`0.100000`、`0.100808` 和 `0.100925`，结果相同；较高召回的相邻候选 `0.106890` 也得到同样的 0.0250 错误率。

阈值候选是对这同一批 40 条案例的 top-1 distance 观测值枚举后选择的，因此属于固定评测集上的工程比较，不是独立测试集上的泛化精度。MiniLM 的具体阈值数值没有在汇总日志中保留，报告只保留其零错误候选的聚合结果。

## 运行成本观察

- MiniLM 模型加载约 10.09 秒，语料向量化约 1.16 秒。
- E5 模型加载约 10.64 秒，语料向量化约 0.17 秒；查询阶段比 MiniLM 快，但仍显著慢于当前词法检索。
- 临时虚拟环境约 1.4 GB；已观察到的模型缓存约 458 MB。该体积来自 PyTorch、Transformers、ChromaDB 及模型运行时，不代表适合当前零成本 Serverless 部署的包体积。
- 当前词法检索不需要下载模型或初始化向量库，冷启动和运行时依赖都更小。

耗时是临时 runner 记录的单次查询 wall-clock 聚合值，未进行跨机器重复、冷启动/暖机分离或显卡对照；只能用于本次环境内的相对比较。原始 embedding、距离列表和临时 runner 没有提交到仓库，因此本报告不声称可复现实验的全部底层细节。

## 结论

**暂不把 Embedding + ChromaDB 部署到线上，也不替换 RAG V1.1。**

理由如下：

1. 在“资料外问题必须拒答”的硬约束下，两个本地模型都需要把阈值收紧到来源命中率 0.5217；当前词法方案在同一 40 条案例上达到来源命中率 1.0、拒答率 1.0、错误率 0。
2. E5 可以用较低延迟换取更高召回，但目前的 0.0250 错误率意味着它会把至少一个边界问题交给模型，和个人资料问答的事实边界目标冲突。
3. 引入 PyTorch、sentence-transformers、模型文件和 ChromaDB 会明显增加冷启动、内存和部署体积；在零成本、快速迭代阶段，收益不足以抵消复杂度。

因此，当前线上继续使用可解释、可审计的词法 RAG V1.1。Embedding + ChromaDB 保留为本地学习和后续对照实验，不在项目文档中描述为已部署功能。

## 后续触发条件

只有在新增项目/博客使资料规模明显增长，或词法检索在扩充后的评测集上出现稳定召回瓶颈时，才重新评估向量检索。下一轮应同时加入：

- 更多经过本人审核的资料和同义改写案例；
- 混合检索（词法候选 + 向量重排）对边界拒答的对照；
- 冷启动、内存、包体积和真实部署平台限制的测量；
- 真实模型回答质量的人工抽查，但仍不得把未审核内容写入知识库。

## 变更边界

- 本轮未修改正式 `backend/requirements.txt`、应用代码、Preview 或 Production。
- 本轮未发起远程 LLM 推理/API 请求；模型权重下载仅写入临时缓存，不进入仓库或部署环境。
- 本轮未修改 `knowledge/profile.md`、`knowledge/spmtrack.md` 或任何资料正文。
