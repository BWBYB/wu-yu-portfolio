# Agent V1.1 检索边界加固设计

## 状态

方案 A 与书面规格已获用户批准，实施计划已生成。

## 背景

Agent V1 已经把完整语料注入升级为无依赖的 Markdown 分片和词法检索。Version 0 离线评测通过真实 `/api/chat` 路径运行 28 条案例，并用 Fake Provider 隔离真实模型成本。

当前基线表现：

- HTTP 成功率、期望来源命中率和关键事实字符串覆盖率均为 `1.0`。
- 10 条资料外或对抗案例中，只有 1 条真正走无命中短路，边界正确率为 `0.1`。
- 错误检索率为 `0.3214`。
- 主要误命中来自姓名、项目名和“系统”“服务”“工作”“大学”等低信息词，以及中文滑动 n-gram 产生的噪声片段。

这说明当前阶段的主要问题是检索精度和调用边界，而不是语料召回不足。直接接入 Embedding 或向量数据库会增加成本和部署复杂度，也不会自动判断资料是否足以支持回答。

## 目标

在不改变公开 API、知识资料和部署方式的前提下，为现有词法检索增加双层门控：

1. 先拦截明确要求编造、泄露内部提示或读取服务器文件的请求。
2. 再要求候选片段至少命中一个能够证明资料支持问题的有效事实词；姓名、项目名和通用系统词只能辅助排序，不能单独触发模型调用。
3. 用少量可审计同义词扩展弥补当前词法检索对常见改写的不足。
4. 用现有 28 条基线和新增变体案例证明边界改善没有牺牲事实召回。

## 非目标

- 不引入 LangChain、LangGraph、ChromaDB、Milvus、Embedding API、分词服务或新的运行时依赖。
- 不修改 `knowledge/profile.md`、`knowledge/spmtrack.md` 或网站个人资料。
- 不改变 `POST /api/chat` 的请求字段、响应字段、状态码或固定无命中回答。
- 不实现通用内容审核、身份认证、权限系统或完整 Prompt Injection 防御。
- 不把规则命中描述成语义理解，也不把离线字符串指标描述成模型回答质量。
- 不修改 Vercel Firewall、环境变量或 Production。

## 方案选择

### 采用：双层词法门控

保留现有 `retrieve_chunks()` 接口和排序流程，在查询特征和候选准入之间增加显式边界：

```text
question
  -> normalize and extract tokens
  -> narrow blocked-request check
  -> alias expansion
  -> candidate scoring
  -> evidence gate
  -> top-k chunks or empty tuple
  -> existing /api/chat short circuit
```

优势：零模型成本、结果确定、可单元测试、适配当前 Vercel Python Function，并能直接解释为什么某个问题没有进入模型。

### 暂不采用：BM25/TF-IDF

BM25 能改善排序，但姓名或项目名仍可能得到高分，不能独立解决“语料相关但问题没有答案”的边界问题。当前只有两个文档和少量片段，排序收益有限。

### 暂不采用：Embedding 与向量数据库

向量检索更适合同义改写和语料扩张，但语义相似不等于资料足以回答。它仍需要边界门控，并会增加索引、密钥、费用和部署维护。本阶段先建立可比较的精度基线，后续再用相同案例评估是否值得替换召回层。

## 检索规则

### 1. 查询清理

保留现有英文、数字、技术名词和中文双字/三字片段提取，但收紧中文噪声：

- 丢弃以常见语法字开头或结尾的 n-gram，例如由“的、了、在、把、请、和、与、不”形成的噪声片段。
- 扩充停用词，覆盖“一个”“信息”“情况”“相关”等不能独立证明资料支持问题的通用词。
- 相同 token 仍只计一次，查询为空或没有有效 token 时返回空结果。

规则针对 token 特征，不比较完整问题文本或评测案例 ID。

### 2. 低信息词

低信息词包括两类：

- 实体锚点：`吴禹`、`SPMTrack`。
- 通用上下文：`系统`、`项目`、`工作`、`服务`、`大学`、`资料` 等。

它们可以为包含有效事实词的候选片段增加排序分数，但不能独立满足最低证据门槛。这样“SPMTrack 使用哪些组件”仍可检索，“SPMTrack 有多少真实用户”不会仅凭项目名调用模型。

### 3. 有效事实词

候选片段必须至少命中一个非低信息 token，或命中同义词扩展后的语料词，才有资格进入 Top-K。技术名词、年份、模式名以及“毕业、岗位、英语、流程、队列、部署、负责、日志、视频、跟踪”等领域事实词属于有效证据。

现有内容分数和标题分数继续用于已通过门槛的候选排序；`top_k=4` 和稳定顺序不变。门槛判断与排序分数分离，避免仅调高 `min_score` 导致事实问题一起丢失。

### 4. 同义词扩展

新增一个小型、只读、可测试的查询扩展表。它只把查询概念映射到语料中已经存在的表达，不生成答案。例如：

- “英语”扩展为“语言能力”和 `CET-6`。
- “求职方向”扩展为“寻找”和“岗位”。
- “贡献”扩展为“负责”和“参与”。
- “多目标跟踪”扩展为 `spmtrack_mot`。

扩展词参与证据门槛和排序，但报告必须继续把关键事实覆盖称为字符串代理检查。扩展表不包含完整问题，不把未知事实映射到任何答案。

### 5. 明确阻断的请求

在评分前检查少量窄范围组合模式：

- 要求编造、伪造或强行声称资料未提供的事实。
- 要求泄露系统提示、隐藏配置、密钥或内部指令。
- 要求读取服务器、本地文件或执行越权文件操作。

命中后直接返回空片段，由现有 API 返回固定知识边界回答且不调用模型。规则必须使用动作与目标的组合，不能因为单独出现“系统”“文件”或“配置”就阻断正常技术问题。

电话号码、薪资、社团和真实用户数等普通资料外问题不建立逐题黑名单；它们应由证据门槛自然返回空结果。

## 模块边界

主要修改 `backend/app/retrieval.py`：

- `retrieve_chunks()` 的参数和返回类型保持不变。
- token 清理、同义词扩展、阻断判断、证据判断拆成小型纯函数。
- 所有规则为模块级不可变集合或映射，不读取环境变量、不访问网络、不调用模型。

`backend/app/main.py`、`backend/app/prompts.py` 和前端原则上不改。现有无命中短路会自动承接空检索结果。如果实现过程中发现必须修改这些文件，需回到规格复核，因为那意味着范围已经扩大。

## 数据流与错误行为

```text
有支持的问题
  -> 有效事实词命中
  -> 返回排序片段
  -> 构造 Prompt
  -> Fake/real provider
  -> 原有 ChatResponse

资料外问题
  -> 只有实体或通用词命中
  -> 证据门槛失败
  -> empty tuple
  -> HTTP 200 固定边界回答，sources=[]，模型调用 0 次

明确对抗请求
  -> 阻断组合命中
  -> empty tuple
  -> HTTP 200 固定边界回答，sources=[]，模型调用 0 次
```

检索器不抛出新的业务异常。模型配置错误和供应商错误仍保持现有 `503`/`502` 行为。

## 评测与防过拟合

### 现有基线

完整运行 28 条 Version 0 案例，目标为：

- HTTP 成功率：`1.0`。
- 期望来源命中率：`1.0`。
- 关键事实字符串覆盖率：`1.0`。
- 资料外/对抗边界正确率：`1.0`。
- `expected_model_call=false` 案例的模型短路率：`1.0`。
- 错误检索率：`0.0`。

### 新增变体案例

增加不少于 12 条检索回归案例，但不把完整问题写入生产规则：

- 至少 4 条实体存在但事实缺失的问题。
- 至少 3 条对抗表达变体。
- 至少 3 条已有事实的同义改写。
- 至少 2 条同时包含低信息词和有效事实词的正常问题。

单元测试还必须覆盖：

- 低信息词单独出现时不返回片段。
- 低信息词与有效事实词组合时仍能命中正确来源。
- 同义词扩展能够恢复原本缺少字面重叠的事实问题。
- 阻断规则需要动作与目标组合，不误伤正常的系统架构或文件格式问题。
- `top_k`、稳定顺序、空查询和英文技术 token 的原有行为不回归。

实现不得导入 `backend/evals/cases.json`，不得按案例 ID 或完整问题生成规则。

## 验收标准

- `retrieve_chunks()` 公共接口和 `/api/chat` 请求响应契约保持不变。
- 不新增运行时依赖，不调用真实模型、Preview 或网络服务完成本地验收。
- 现有 28 条评测达到本规格定义的全部目标指标。
- 新增不少于 12 条变体测试全部通过，且生产规则不包含完整评测问题。
- 后端完整测试、前端测试、Astro check、Astro build 和 `git diff --check` 全部通过。
- 报告如实说明规则检索的适用范围，不宣称已经获得通用语义理解或完整安全防护。
- Vercel、环境变量、Firewall、Production 和知识资料保持不变。

## 后续决策点

当资料扩展到更多项目或博客后，用同一评测框架比较三类方案：当前词法门控、BM25/混合检索、Embedding 检索。只有新方案在同义改写召回和边界精度上都有可测提升，且成本和部署复杂度可接受时，才替换当前召回层。
