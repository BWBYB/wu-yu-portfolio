这篇文章记录个人知识库 Agent 的第一轮工程基线。当前系统只有两份固定 Markdown 资料、轻量关键词检索和一个 FastAPI `/api/chat` 入口，还没有接入 Embedding、向量数据库或 Agent 框架。先把现状测清楚，再决定下一步技术投入。

## 为什么先做离线评测

如果每次修改检索器都依赖真实模型回答，成本高、结果不稳定，也很难判断问题来自资料、检索还是模型。Version 0 使用 FastAPI 的真实请求路径，但在评测进程中临时替换模型适配器为 Fake Provider，因此不会调用中转站或消耗 API 额度。

## 案例与观察边界

评测集包含个人事实、项目事实、同义改写、资料外问题和对抗问题五类，共 28 条。每条结果只保存案例 ID、HTTP 状态、来源列表、检索片段数量、模型调用次数、耗时和关键事实代理命中情况，不保存完整问题、回答、请求头或供应商原始异常。

关键事实覆盖是字符串检查，不是语义正确率；来源命中也只表示检索返回了预期资料。真正的回答质量、拒答措辞和提示词注入抵抗力仍需要人工复核。

## 第一轮结果

事实案例的来源命中率和关键事实字符串覆盖率均为 1.0，说明当前两份资料对已经写入的项目和个人信息有稳定覆盖。真正无命中的边界案例没有调用模型，保留了成本边界。

同时，资料外和对抗案例中有一部分因为包含“吴禹”或“SPMTrack”等已知词而误命中资料。当前基线的资料外正确拒答率为 0.1，错误检索率为 0.3214。这个结果不是评测失败，而是准确暴露了关键词检索把“提到已知实体”和“问题可被资料支持”混在一起的问题。

## 下一步怎么选技术

下一步先围绕误命中和同义改写补充检索评测，再比较 RAG V1 的查询改写、向量检索或混合检索。只有在检索边界稳定后，才有必要把 RAG 封装成工具，进一步尝试 Function Calling、MCP 或 Agentic RAG。

这轮基线也提醒我：一个能调用模型的聊天页面还不是完整 Agent。工程上需要同时说明资料来源、失败模式、成本边界和可重复的验证方法。
