## 1. 为什么先用 Dify 验证

这次的目标不是马上做一个完整的 Agent 平台，而是先确认三件事：资料能否稳定导入、切分后的片段能否被召回、模型能否根据召回内容回答问题。

Dify 适合作为这个阶段的验证编排器。它可以快速展示知识库、切分参数、召回片段和工作流结果，让我先观察 RAG 的真实行为，再决定哪些部分值得用 LangGraph、FastAPI 和 ChromaDB 自己实现。当前工作流仍然是“用户输入 -> 知识检索 -> LLM -> 直接回复”，它是一个 RAG 问答流程，不等于已经完成了自研 Agent。

## 3. 当前流程与切分配置

```text
Agent Book chapter1/2/3
        |
        v
本地 Embedding 服务（E5 Small）
        |
        v
Dify 知识库（共享向量索引）
        |
        v
用户问题 -> 知识检索 -> GPT-6.1 Sol -> 直接回复
```

当前沿用的切分配置如下：

- 通用文本切分；
- 最大分段长度：`1024`；
- 重叠长度：`50`；
- 清洗连续空白；
- 高质量向量索引；
- Embedding：本地 `E5 Small`。

这里的“分段”是导入或重新处理文档时进行的。一次查询不会重新切分文档，只会把问题向量化并从已经建立的索引中检索片段。

## 4. 召回验证方法

我没有把相似度分数直接称为准确率。当前记录三个更清晰的信号：

- **Top-1 章节命中**：最高分片段是否来自预期章节；
- **Top-3 包含预期章节**：前三个片段中是否至少有一个来自预期章节；
- **内容相关性**：片段是否真的覆盖问题，而不只是包含相似词。

每个问题返回 3 个召回段落。下面的“最高分”是 Dify 页面显示的相似度分数，不代表答案正确率。

## 6. 跨章节与资料外边界

### 跨章节问题

问题：`Agent 如何同时利用上下文和长期知识？`

结果的三个片段中，前两个来自第 1 章，第三个来自第 3 章，最高分为 `0.91`。这符合问题本身同时涉及上下文、用户记忆和知识检索的特点。它也说明跨章节问题不能简单用“是否命中一个章节”来评价，需要检查多个片段能否共同支撑答案。

### 资料外问题

问题：`吴禹在 SPMTrack 项目中负责什么？`

最高分仍有 `0.86`，但返回的是时间戳、流程状态管理等 Agent Book 片段，与 SPMTrack 无关。这是一个重要的失败边界：相似度不低，不代表知识库真的有答案。

因此，资料外问题必须结合内容相关性和提示词约束处理。当前 Chatflow 的系统提示词已经改为：

> 你是 Agent Book 前三章问答助手。只能依据已连接的第 1、2、3 章知识库资料回答，不得使用常识补充或编造。如果检索资料没有覆盖用户问题，请明确说“前三章资料未覆盖这个问题”。

在工作流 Preview 中，问题“用户记忆和知识库有什么区别？”已成功返回与第三章内容相关的回答，但模型将其标注为第 2 章资料；这与召回测试中的第三章来源不一致，因此不能算作可靠的章节引用验收。它说明提示词已经更新，但来源章节归因仍需要继续校准。这里也提醒我：工作流展示的章节名称和检索片段来源必须一起复核，不能只看模型回答文本。

## 8. “学习资料问答工作台”是否值得做

这个方向值得做，但目前更适合作为个人学习和求职展示的 MVP，而不是立即做成多用户 SaaS。最小版本可以只解决一个明确问题：把 Markdown 或 PDF 资料导入后，经过切分和向量化，能够检索、回答并展示来源。

建议的 MVP 边界：

1. 导入 Markdown/PDF；
2. 展示切分结果和索引状态；
3. 支持知识库检索问答；
4. 回答中展示来源文档和章节；
5. 保存少量召回测试记录。

暂时不做多用户权限、在线协作、计费、复杂工作流市场、多 Agent 和大规模异步任务。这些功能会分散当前“把 RAG 做扎实并能解释验证过程”的目标。

## 9. 现成方案与后续路线

| 方案 | 适合用途 | 当前判断 |
| --- | --- | --- |
| Dify | 快速搭建知识库和工作流 | 当前验证工具，适合先看效果 |
| AnythingLLM | 本地个人资料问答 | 可作为本地产品体验的对照方案 |
| Open WebUI + RAG | 本地模型和聊天界面组合 | 适合已有本地模型的用户 |
| LlamaIndex/LangChain | 自己控制索引、检索和应用代码 | 适合后续重写 RAG 核心 |
| LangGraph + FastAPI + ChromaDB | 可解释、可展示的求职项目 | 适合稳定验证后再实现 |

当前路线保持为：

```text
Dify 验证前三章
        ->
记录召回问题与失败案例
        ->
形成博客和技术记录
        ->
用 LangGraph/FastAPI/ChromaDB 重写最小版本
        ->
再考虑接入个人网站或 OpenShip
```

这个顺序的价值在于，先获得真实的切分、召回和拒答经验，再决定代码架构。求职时可以清楚区分：哪些是 Dify 配置验证，哪些是后续自己实现的工程能力。

## 10. 当前结论

- Agent Book 前三章已导入同一个本地 Dify 知识库；
- 章节专有问题的召回较稳定，跨章节基础概念存在语义干扰；
- 资料外问题可能出现高分误召回，不能只用相似度判断答案存在；
- Chatflow 已更新为前三章范围，并通过一个第三章问题的未发布 Preview 验证；
- 本阶段不统计 token 成本；
- 下一步应先固定这版验证记录，再决定是否进入 LangGraph/FastAPI/ChromaDB 的自建 RAG 实现。
